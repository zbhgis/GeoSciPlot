# GeoSciPlot

地学科研绘图参考图库 —— 收集公开发表的地学 / 科研图表，供绘图风格、配色与版式参考。

在线浏览：<https://geosciplot.zbhgis.com>（部署后生效）

## 一、展示逻辑

```
首页 index.html
├─ 头部：站名 / 标题 / 一句话说明 / 统计行（共 N 张 · X 种期刊 · Y 个标签 · Z 个上传日期）
├─ 工具条：关键词搜索 + 排序下拉 + **每页数量（24 / 48 / 96 / 显示全部）**
│          + **筛选折叠按钮** + 重置筛选
├─ 筛选区（**可折叠**；4 个维度，每个维度单选，维度之间是 AND：
│    标签 tag ｜ 期刊 journal ｜ 论文发表年份 published ｜ 上传日期 added）
│    └─ 折叠后按钮显示已选条件数量，悬停可看到具体条件
├─ 网格：**多列瀑布流**（2/3/4 列响应式，每列独立堆叠），**默认每页 48 张**，只渲染当前页
│    └─ 卡片 = 缩略图 + 一行标签（超出用省略号，鼠标悬停显示完整标签）
└─ 分页条：← 上一页 ｜ 第 X / N 页 ｜ 下一页 →（首/末页对应按钮自动禁用）

点击卡片 → 详情页 /{id}/
├─ 原图（**不压缩**，按原始尺寸展示，最大 86vh）
├─ 元信息表：ID / 期刊 / 论文发表 / 上传日期 / **被浏览 N 次** / 标签
│    ├─ 被浏览读取统计服务的按 path 计数（本地预览无 /api/ 反代时显示「…」）
│    └─ **标签可点击** → 回到首页并自动套用该标签的筛选（链接形如 /?tag=标签）
└─ 上一张 / 下一张（按当前索引顺序）
```

> **为什么用瀑布流而不是 grid**：grid 的同一行会被"最高的那张卡片"定高，
> 宽高比差异大时（本项目有 1280×444 超宽图和 825×1280 竖幅图），
> 同行矮卡片下方必然空出一大片 —— 这是之前"卡片上下空白多"的根因。
> 多列瀑布流让每列独立堆叠，彻底消除该问题。

- **链接可携带筛选参数**：`/?tag=标签&q=关键词&journal=期刊&pub=年份&added=日期`，
  打开即自动套用（标签跳转就是用它实现的），因此任何筛选结果都可以分享 / 收藏
- **每图浏览量的后端**：`/api/v1/stats/views?prefix=/geosciplot/`（按 path 计数，
  统计服务新增接口）——部署子域时记得 Nginx 反代 /api/，否则详情页的浏览量不显示

- **排序**：按上传日期（默认，新→旧）· 按论文发表时间（新→旧）
- **搜索范围**：id + 期刊 + 发表时间 + 上传日期 + 标签 + 说明（小写子串匹配，支持中文）
- **分页的意义**：只渲染当前页的卡片 → **只请求当前页的缩略图**。
  130 张时实测：DOM 里只有 48 个卡片、只加载 48 张图（而不是全部 130 张）。
  这是图库上规模后最关键的一条，越早生效越好。
- 筛选 / 搜索 / 排序变化时自动回到第 1 页。

### 图片的身份：唯一 id，没有标题 / 分类

- **id** = 图片内容 sha1 前 10 位（如 `d57d821bbd`），与文件名无关，天然唯一且稳定
- 图片**不设标题**，前端展示以 id 为准
- **分类维度已取消**：GitHub 上的目录现在承载"上传日期"而不是分类，见第三节

## 二、本地管理界面

```bash
python scripts/admin.py            # 自动打开 http://127.0.0.1:5199
```

界面流程：**拖拽上传 → 逐张填信息 → 点发布**。发布时自动依次执行：

```
写 meta/titles.csv → prepare.py（压缩+索引）→ build_site.py（生成站点）
→ git add / commit / push
```

- **只有本机能访问**：服务只绑定 `127.0.0.1`，"仅我可访问"由网络拓扑天然满足，不需要登录
- **不需要任何 token**：推送用你本机已配置的 git 凭据（SSH key 或凭据管理器）
- 上传时按内容算出 `id` 并生成预览缩略图；**重复上传同一张图会被识别并标记**
- 表单字段：**期刊 / 论文发表 / 标签 / 说明**（没有标题和分类）
- 界面显示每步日志；目录还不是 git 仓库时提供「初始化仓库」入口

## 三、GitHub 上的目录结构：按上传日期分文件夹

```
images/thumb/2026-09-11/{id}.webp      ← 列表缩略图（压缩，480px WebP）
images/thumb/2026-09-12/{id}.webp
images/full/2026-09-11/{id}.{ext}      ← 详情页原图（逐字节副本，不压缩）
images/full/2026-09-12/{id}.{ext}
```

- **目录名 = 该图首次进入管道的日期（即上传日期）**，同一天上传的图放在一起
- 重新生成时沿用索引里记录的日期，**路径保持稳定**（不会因为重新构建而变动）
- 前端已**不再有分类**；旧数据里的 `title` / `category` 字段保留在 `meta/` 里
  （迁移期兼容），但界面不再使用

## 四、数据字段（`meta/refs.json` 每张图一条）

| 字段 | 来源 | 说明 |
|---|---|---|
| `id` | 自动 | 图片内容 sha1 前 10 位，唯一且与文件名无关 |
| `added` | 自动 | 上传日期 `YYYY-MM-DD`，同时是 images 下的目录名 |
| `journal` | 人工 | 期刊名（**当前为占位数据，需按原论文核对**） |
| `published` | 人工 | 论文发表时间 `YYYY-MM`（**当前为占位数据**） |
| `tags` | 人工 | 标签（`|` 分隔），参与搜索 |
| `desc` | 人工 | 一句说明（图面要点），参与搜索 |
| `thumb` | 自动 | `thumb/{日期}/{id}.webp` |
| `full` | 自动 | `full/{日期}/{id}.{ext}` |
| `width` `height` `ext` `bytes` `origName` | 自动 | 尺寸、扩展名、体积、原始文件名 |
| `title` `category` | 人工 | **历史遗留字段**，前端已不使用 |

## 五、仓库结构

```
raw/                  原图投放区（**本地收件箱，已 gitignore**；文件名随意，扁平投放）
images/thumb/{日期}/  自动生成：列表缩略图（长边 ≤480，WebP q78）
images/full/{日期}/   自动生成：详情页原图副本（原始字节，不压缩）
meta/refs.json        自动生成：索引（前端唯一数据源）
meta/titles.csv       人工编辑：journal/published/tags/desc（Excel 可开）
scripts/admin.py      本地管理界面（仅本机可访问）
scripts/admin_ui.html 界面文件
scripts/prepare.py    图片规范化 + 索引生成
scripts/build_site.py 静态站生成（site/）
gallery.config.json   站点配置：GitHub 用户名、图片源顺序、OSS 桶
site/                 生成的静态站点（部署产物，已 gitignore）
```

> **原图只存一份**：`images/full/` 是原图的逐字节副本（文件名是干净的 id），
> 所以 `raw/` 只作为本地投放收件箱，不重复入库 —— 省掉一半仓库体积。
> 在新机器上重新跑管道时，把需要重处理的图从 `images/full/` 拷回 `raw/` 即可。

> ⚠️ `journal` 与 `published` 目前是**占位模拟数据**（按图面内容推断），
> 正式发布前请按原论文核对 —— 标错期刊属于学术不端。

## 六、手动加图（三步，不想用界面时）

```bash
# 1. 把图片丢进 raw/
# 2. 导出编辑表，用 Excel 填 journal / published / tags / desc
python scripts/prepare.py --export-csv

# 3. 回填并生成站点
python scripts/prepare.py
python scripts/build_site.py            # 生产构建
python scripts/build_site.py --preview  # 本地预览（图片走本地副本）
```

本地预览：`cd site && python -m http.server 5190` → <http://127.0.0.1:5190>

## 七、图片规格

| 用途 | 路径 | 长边 | 质量 | 格式 |
|---|---|---|---|---|
| 列表缩略图 | `images/thumb/{日期}/` | ≤480 | 78 | WebP |
| 详情页原图 | `images/full/{日期}/` | **不缩放** | **不重编码** | 原格式 |

> 📌 **jsDelivr 实测更正**：网上常说「仓库超 50MB 就不能用 jsDelivr」，实际验证下来
> **文件分发不受仓库体积限制**（3GB+ 的仓库文件仍能正常返回 200），受限的只是它的
> **文件列表 API**（我们不需要那个功能）。真正要留意的是：
> - jsDelivr 不服务**单个大于 20MB 的文件**（我们的图都在 1MB 量级）
> - GitHub 自身建议仓库 <1GB、强烈建议 <5GB

## 八、图片加载：三源自动降级

按 `gallery.config.json` 的 `activeSource` 顺序尝试（当前：GitHub 链接优先）：

1. `jsDelivr` — 本仓库内容的 CDN 分发层（默认首选）
2. `GitHub raw` — 仓库原始直链
3. `OSS` — 阿里云对象存储兜底

> 生产构建**不打包图片**：站点只发 HTML/JS，图片全部由 GitHub（jsDelivr/raw）分发，
> 服务器带宽不被图片消耗。本地预览构建（`--preview`）会把图片副本放进 site/ 同源加载。

> 降级是**逐图自动**的：任一源加载失败，该图自动换下一个源，全部失败才显示占位块。
> 切换顺序只需改 `gallery.config.json` 的 `activeSource` 数字，无需改代码。

任一源加载失败，**逐图自动切换**到下一个源；全部失败才显示占位块。
切源只需改 `activeSource` 一个数字，无需改代码。

## 九、访问统计

每张图的详情页会向后端上报一次访问（复用 `www.zbhgis.com` 的 FastAPI 统计服务，
子域 Nginx 反代 `/api/` 实现同源）。统计 path 形如 `/geosciplot/{id}`，
因此后台可按图查看 Views / Visitors。

## 十、规模扩展

按现有图片均值（原图 ~558KB、缩略图 ~23KB）推算：

| 图片数 | 原图 | 缩略图 | 仓库合计 | 首页单次浏览拉取 |
|---|---|---|---|---|
| 10 | 5.5 MB | 0.23 MB | 5.7 MB | 0.23 MB |
| 100 | 55 MB | 2.3 MB | 57 MB | 0.23 MB |
| 500 | 272 MB | 11 MB | 284 MB | 0.23 MB |
| **1000** | **545 MB** | **23 MB** | **568 MB** | **0.23 MB** |
| 3000 | 1.6 GB | 69 MB | 1.7 GB ⚠ | 0.23 MB |

**已解决**：分页 + 按页渲染 → 无论多少张图，首页单次浏览只拉当前页（48 张）的缩略图。

**到 1000 张量级时仍建议做**：把原图移出 git（它占仓库体积的 96%）——
仓库只留 `images/thumb/`（1000 张 ≈ 23MB，clone 秒级）+ `meta/`；
原图放 OSS（存储 545MB ≈ 0.065 元/月），详情页的 `full` 改为指向 OSS 的绝对 URL，
同时把 `activeSource` 切到 OSS/CDN（国内访问也更稳）。
